# Google offline authorization component comparison

Evaluated 2026-10-02 before selecting or deploying anything. Zen needs a phone to open official consent while its paired, private daemon receives and retains the account token and can continue authorized work after the phone leaves. The product owns app registration and any confidential client secret. Neither a global backend key nor the Google client secret can be distributed to user daemons.

| Option | Current license / free and paid boundary | Credential and deployment model | Fit for Zen |
| --- | --- | --- | --- |
| Nango free self-hosted Auth/Proxy | Current root license is Elastic License 2.0, source-available with hosted/managed-service and license-key restrictions. Official docs offer free Auth/Proxy; syncs, tools, webhooks, MCP server, custom auth branding, RBAC/MFA/audit features are outside that free tier. Enterprise BYOC/Self-Managed requires an annual subscription. | Auth service and Postgres retain encrypted user credentials; documented self-managed platform includes Redis and other optional/full-feature services. Get-connection API can return refresh tokens, refreshes expired access tokens, and uses a backend environment API key. | Closest maintained turnkey integration component. Self-hosting avoids third-party custody, but still centralizes refresh tokens. A Zen gateway must authenticate individual daemon flows, restrict each daemon to its connection, and deliver only its own tokens. Never ship an environment key. Copying tokens once and deleting the Nango connection loses managed refresh. Keeping it requires explicit product-side persistent custody and operational/licensing review. No free-tier deployment or contract has been accepted. |
| Keycloak identity brokering | Apache 2.0; maintained identity server with self-hosting. No paid gate identified for core brokering. | Runs an identity service/database with realms, users, sessions, provider registration and external token storage. Current docs recommend Identity Brokering APIs; legacy external token exchange V1 is deprecated. | Strong choice if Zen already operates Keycloak for user identity, which is not established. Adds a user/realm/session model to a paired-server product. External tokens still require a linked identity and provider-token storage; no demonstrated one-shot daemon-bound encrypted delivery or secret-free daemon refresh. Do not build on deprecated V1. Not the minimum new deployment for one Google integration. |
| Maintained OAuth client libraries: Go `golang.org/x/oauth2`; `openid-client` for a JS host | Go OAuth2 uses BSD-3-Clause; openid-client is MIT, with current v6.8.8 release2026-09-05. Both provide OAuth protocol machinery, not a hosted integration product. | Application supplies public HTTPS callback, state/PKCE persistence, secret storage and delivery authorization. Libraries handle code exchange/refresh. | Lowest platform overhead; custom flow-to-daemon binding still needs review and tests. Prepared Go candidate already uses maintained OAuth2 and authenticated public-key encryption. Switching languages to openid-client does not remove the binding responsibility, so there is no reason to add a separate JS service solely for its library. |
| Official Android/iOS Google SDKs | Maintained vendor SDKs; product still needs correctly typed registered clients, applicable Google terms and verification. | Phone-native online authorization. Android offline authorization requests a server auth code for a Web client; the backend exchanges it using the confidential client registration. | Native UI can improve authorization entry, but does not eliminate the backend secret needed for Android plus an offline private daemon. An iOS-only custom redirect is not proof of Android parity. Do not register a desktop/TV app to evade mobile constraints. |
| Prepared Zen Google-only exchange candidate | Zen repository code plus maintained Go OAuth2/crypto dependencies; no hosted service purchased. | One product-owned HTTPS component, fixed Google provider/scopes/callback. Ephemeral single-use flow, cookie/state/PKCE, result encrypted to original daemon key; daemon vault keeps tokens. Refresh presents the daemon-bound receipt and token to product-held secret exchange. No persistent user-token database. | Smallest fit to current custody and paired-server model, but bespoke binding/abuse controls must receive security review and real consent/refresh/return verification. It is not independently audited or accepted merely because fixtures pass. See exact config/protocol in the candidate artifact. |

Recommendation for Brain: do not provision Nango or Keycloak solely to unlock this one provider yet. Nango is the strongest maintained full component, but its current credential custody and daemon access boundary require a Zen gateway anyway; its free/source-available status is not equivalent to a permissive, unrestricted OAuth hosting license. If product-side persistent token custody becomes acceptable or an existing licensed Nango/Keycloak deployment is confirmed, prefer evaluating that maintained installation before custom deployment. Under the currently specified daemon-custody boundary and absent existing infrastructure, retain the narrowly scoped Go exchange as the leading candidate **subject to owner/host choice and security review**, without deploying it now. This recommendation follows the comparison; it does not authorize a new host or legal agreement.

The concrete minimum owner inputs are a Google Cloud project/account actually controlled by Zen and an existing HTTPS host that may hold its Web-client secret. Google callback must exactly equal that chosen origin plus `/google/callback`. No generic callback supplied by the phone is trusted. Initial result and each refresh remain bound to the daemon that started the flow; changing the selected server cannot transfer a pending account. The phone/browser never receives the refresh token or product secret. If Nango is chosen instead, a reviewable adapter must additionally prove per-daemon access isolation, exclude its global API key from every daemon, and document retained central token custody before implementation is called complete.

No component was installed, no registration performed, no terms accepted, no paid plan or public host created for this evaluation. Source/docs research is distinct from actual deployment testing. Google consent, read/disconnect/reconnect and real iOS behavior remain unverified.
